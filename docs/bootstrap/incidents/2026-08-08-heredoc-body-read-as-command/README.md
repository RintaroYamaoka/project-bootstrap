# 2026-08-08 — heredoc 本文をコマンドと誤読し、規律の説明そのものを block した

**発見**: ai-reception の開発体制入れ替え (kanban-flow → bootstrap 全面移行、#477) 中に
利用者が遭遇し、最小再現つきの incident として起票された
(`ai-reception:docs/bootstrap/incidents/2026-08-08-block-add-all-heredoc-false-positive/`)。
本 repo 側の記録はその修正と教訓の側を持つ。

**種別**: false positive (通すべき操作を止めた) / 原則②「信号選び」の違反
**修正**: ADR 0025、v0.35.0 (`lib/parse-command.sh` に heredoc 本文の除去を追加)

## 何が起きたか

commit メッセージの heredoc に「一括 stage は `git add -A` を使わない」という**規約の
説明**を書いた commit が block された。`cat <<'EOF' … EOF` のように git と無関係な
コマンドでも起きる。

gate は「コマンド文字列」を走査するが、**heredoc 本文は実行されるコマンドではなく
stdin に渡されるデータ**である。この区別が無かったため:

- token walker (`lib/git-invocation.sh`) は改行を単なる空白として word-split し、本文の
  トークンがコマンド列に流れ込んだ
- raw regex 経路 (`block-dangerous-git-ops.sh`) は本文の字面をそのまま拾った

## なぜ「安全側だから良い」で済まないか

止めていたのは **この規律そのものを文章で説明する行為**だった。規律を運用している repo
ほど、禁止コマンドの字面を書く機会 (CLAUDE.md・PR 本文・commit メッセージ・incident・
hook のドキュメント) が多い。発見時、実際に `/permissions` で hook を deny にする案が出た。

これは繰り返し警告してきた **「gate が自分の bypass を作る」** の実例である。
false positive は「安全側」ではなく、**規律を回避する動機**という別の危険を作る。

## 教訓 (memory へ昇格した分)

1. **gate の信号は「テキストの字面」でなく「実行される行為」**。字面は proxy であり、
   データ (heredoc 本文・引数の値) とコマンドを混同する。原則②の具体形が 1 つ増えた
2. **誤検知の重さは「止めた対象が何か」で測る**。同じ 1 件でも、止めたのが
   「規律の説明」なら、それは規律を殺す方向に働く
3. **修正は単一の入口で**。誤検知が 2 つの検出経路 (walker / raw regex) に在ったので、
   walker だけ直すと片肺だった。全 gate が通る `parse_command` が唯一の単一点
4. **緩める修正には fail-closed の例外を必ず置く**。heredoc 本文を落とすのは検出を
   緩める向きなので、`bash <<EOF` のように**本文が実行される形**は落とさない

## 検証で分かったこと (mutation testing の実効)

修正後、実装に 5 つの変異を注入してテストが殺すか確認した。**2 件が生存**した:

- **`<<-` のタブ除去を消す変異が生存** → **本物のテストギャップ**だった。
  `<<-` のテストは終端の後ろにコマンドが無かったため、タブ除去を消しても
  「終端不一致 → 未終端として末尾まで落ちる」で**出力が同じ**になっていた。
  しかもその差は「終端の後ろの実 `git add -A` を飲み込む」= **検出漏れ (fail-open)** の
  向き。終端後に実コマンドを置くテストを追加して kill を確認した
- herestring ガードの変異は生存したが、これはラベル走査が既に `<` を弾くための
  **等価変異** (テストの弱さではない)。コードにその旨を明記して残した

**教訓**: 「テストが緑」は実装を握っている証拠にならない。とくに
**「壊しても同じ出力になる経路」は、差が出る入力を足さないと永久に検出されない**。

## リリース後の実査 (2026-08-08、verification plan の DROP 行を閉じる)

修正 PR の verification plan は「発見元での実査」を **理由つき DROP** にしていた
(別 repo の作業ツリー状態に依存し、merge 前には再現環境を固定できないため)。
v0.35.0 のリリースと配備の後に実行し、以下を確認した。

**配備の確認 (merge ≠ deployed)**: 手元の plugin が v0.35.0 で、実体に
`strip_heredoc_bodies` が入っていることを先に確認した (配備前に「直った」と言わない)。

**誤検知が消えたこと** — 発見元 (ai-reception) で incident の最小再現をそのまま実行し、
通ることを確認。さらに**実際に踏んだ形** (`git commit -F -` の heredoc に規約文を書く) を
使い捨て repo で再現し、本物の commit として成立することを確認した。

**検出が壊れていないこと** — 配備版の hook 実体に 6 ケース。誤検知 2 形は pass、
実行される 4 形 (裸 / heredoc 終端の後ろ / `bash <<EOF` の本文 / `git commit -am`) は
block のまま。**誤検知だけが消え、検出の射程は狭まっていない。**

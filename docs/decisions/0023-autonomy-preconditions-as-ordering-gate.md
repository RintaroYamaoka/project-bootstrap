# 0023 — 自律稼働の事前条件を、発注 commit の precondition として fail-closed 強制する

- **Status**: Accepted
- **Date**: 2026-08-07
- **Deciders**: Rintaro Yamaoka
- **References**: ADR 0022 (上流の統合) / ADR 0018 (信号は tree でなくこの commit) / ADR 0021 (commit 関所と edit 時 gate を作らない理由) / ADR 0007 (verification plan を merge の precondition に)

---

## Context (背景)

AI に長時間の自律稼働をさせるほど、**人間が途中で判断する回数の割合は下がる**。
やり取りを減らすほど AI は途中で新しい情報を受け取れず、仕様に矛盾や欠落があれば
**質問せずにもっともらしい解釈を選ぶか、停止する**。したがって自律稼働時間を延ばす唯一の方法は
「開始前に与える情報を増やす」ことになる。

必要な情報は経験的にこれだけある: 目的 / 作業範囲 / **変更してはいけない範囲** / 守るべき既存条件 /
**優先順位** / **例外時の判断方法** / 検証方法 / 完了条件 / **再試行上限** / **エスカレーション条件**。

前身 2 実装の作業指示テンプレートを実物で確認したところ、**太字の 5 つを 1 つも持っていなかった**:

- `upstream-process` の作業依頼書 = 4 節 (前提 / 実現してほしい振る舞い / あなたが決めること / 依存する未決課題)
- `kanban-flow` のカード = 6 節 (通す価値 / 継ぎ目 / 触るファイル / 決めてよいこと / 決めないこと / 完了の条件)

停止条件・再試行上限・予算・例外時の判断方法・優先順位を書く欄が**物理的に存在しない**。
利用者の症状「仕様の穴が埋まらない」は、規律の緩みではなくテンプレートの欠落だった。

同時に、両者とも強制を 1 つも持たなかった。`upstream-process` はその理由を
「判断を検出する gate は dead code になる」と説明していたが、これは①の分解の失敗である。
「この仕様は正しいか」は既約な判断でも、**「事前条件が記入済みである」は precondition であり
強制できる** (TDD hook が test の質でなく存在を強制するのと同型)。

## Decision (決定)

作業指示書 (WO) を **12 節固定の 1 ファイル**とし、**`status: ordered` の WO を commit する
行為**を信号に、完全性を fail-closed で検査する (`block-commit-if-wo-incomplete.sh`)。
併せて、新規 source 面の作成を信号に、それをカバーする発注済み WO の存在を要求する。
被覆の判定は **編集時 (`block-impl-without-wo.sh`) と commit 時 (`block-commit-if-impl-uncovered.sh`)
の二層**にする — ADR 0017 と同型の理由で、編集時 matcher だけでは `cat > src/x.ts` / codemod /
scaffolder / `cp` が関所を一度も通らず、書き込み方式を列挙して塞ぐのは whack-a-mole だからである。
**lane gate では代替できない**: `order` は WO の 2 節から `.bootstrap/lane` を作るので、WO を 1 枚も
発注していない状態では lane marker 自体が存在せず lane 関所は fail-open する。「発注しないまま
実装を始めた」という、この層が止めたい当の状態が、そこだけ素通りしていた。

検査する precondition:

1. 12 節すべてが記入済み (placeholder `<...>` が 1 つでも残る節は未記入。
   節ごと欠けているのも未記入 = 構造に対して fail-closed)
2. **検算**: DoD (8 節) の行数 = 検証方法 (9 節) の行数、かつ 1 対 1 に対応
3. 事前レビュー (12 節) が全行 `closed` か `deferred:<未決ID>`。
   **表が空 = 未実施も落とす** (未実施と「指摘ゼロ」は別物)
4. `retry_limit` / `budget_tokens` が正の整数 (停止条件の数値半分)
5. 未決台帳との突合 — (a) 4 節が参照する未決が `OPEN` のままでない (b) 4 節の参照先が台帳に
   **実在する** (c) 12 節が `deferred:<id>` で決着させた先が台帳に **実在する**。
   (c) が無いと表の *形* だけを見ることになり、`deferred:U99` のような台帳に無い ID が決着として
   通る = 「名前をつけずに先送りする」という、両前身が共通して禁じていた手そのものが素通りする。
   charter.md が無いまま未決 ID を参照した場合も落とす — 判断材料ごと消えた検査を無音で
   スキップすると、他の節の検査は効いたままなので「gate は効いている」ようにしか見えない

**なぜ commit で、edit 時ではないか** (ADR 0021 と同型の理由): PreToolUse では結果ファイル
全体が存在しない。Edit は断片しか運ばず、`status` の反転と、それを無効化する節の編集は
別々の Edit で来うる。commit は成果物全体が初めて存在し、かつ**それを公開する行為**そのもの
であり、sed / script 経由の書き込みも同時に捕まる (ADR 0017)。

**なぜ tree 全体でなく、この commit が運ぶ WO だけか** (ADR 0018 の適用): tree 全体を見ると、
未完成の draft を 1 枚置いた瞬間に無関係な commit が全部止まり、最短の逃げ道が
「その WO を消す」になる — gate が自分の bypass を作る。

**読む中身は index の版** (`-a` のときだけ worktree): 「この commit が運ぶ file」を index から
取りながら中身を worktree から読むと、部分 stage (`git add -p`) や stage 後の編集で
**検査した中身 ≠ commit される中身**になる。完全性検査がそのズレを踏むと fail-open (未完成のまま
通る) 側に倒れるので、解決を `lib/commit-files.sh` の `commit_file_content` に単一権威化した。

**なぜ `draft` を止めないか**: 起草はまさに思考の場である。そこを止めると、checkpoint を
保存するために節をノイズで埋める誘因が生まれ、gate は形式的に通るが中身は空になる。
**発注 (= AI に渡す行為) だけを関所にする。**

**採用しなかった代替案:**

- *節の「質」を検査する* — 「この停止条件は妥当か」は既約な判断。強制しようとすると
  誤検知で信頼を失い、marker を消される。質は `pre-review` (判断) が見る
- *節を増やして網羅性を上げる* — 12 節でも既に多い。前身の敗因は記憶の負担であり、
  増やせば同じ死に方をする。追加は ADR 0024 の metric で必要性が示されたときだけ
- *edit 時に警告だけ出す (advisory)* — 忘れられる。本プラグインが一貫して採らない形式

## Consequences (結果)

### 良い影響

- 上流の成果物が「人が読む文書」から**機械検証可能な契約**になった。前身 2 実装が
  持てなかった強制が、①の分解を当てるだけで成立した
- 発注 → 実装 → 統合の各段で違う関所が違う問いを見る構成になった
  (完全性 = 発注 commit / 被覆 = 新規 source 面 / 範囲 = lane / 検証 = merge)
- 「未決を無音で埋めない」という両前身唯一の共通不変条件が、初めて機械で守られる部分を持った

### 悪い影響 / トレードオフ

- **発注のコストが上がる**。12 節を埋めて事前レビューを通すまで実装を始められない。
  小さすぎる作業に WO を切ると純損になるため、粒度の下限 (「価値の 1 単位が通る」) を
  `order` skill に明記した。過剰かどうかは ADR 0024 の metric で判定する
- placeholder 判定は「行全体 (または表のセル全体) が `<...>`」という構文規則に依存する。
  意図的に緩い規則で、`Promise<void>` のような行中の山括弧は通す。
  **本文を書いたつもりで山括弧だけの行を残すと未記入と判定される**のは仕様
- 検査は「1 対 1 か」までで、「そのオラクルが良いか」は見ない。そこは `verification` skill
  (ADR 0007 / 0016) の管轄

### 移行後に必要な保守

- WO の様式 (`templates/.../wo/TEMPLATE.md`) と判定エンジン (`hooks/lib/wo.sh`) の
  **節番号は同期していなければならない**。片方だけ変えると gate が無音で緩む。
  `tests/hooks/wo.test.bash` が実テンプレートを読んで「全 12 節が未記入と判定される」ことを
  検査しているので、節を増減したらここが落ちる (= 同期漏れが検出される)
- サーバ側 (CI) twin はまだ無い。ローカル hook は GitHub の Merge ボタンを止められないので、
  実運用で 1 巡してから ADR 0012 の二層化に載せるか判断する
- **CI twin が無いぶん、配備漏れが致命的**: 3 本 (完全性 / 被覆 edit / 被覆 commit) は
  `scripts/doctor.sh` の `REQ` に登録済みで、`docs/bootstrap/commission/` を採用した vendoring
  先で 1 本でも欠ければ `partial` として鳴る。**hook を足すたびに REQ を直す**
  (`MAINTENANCE.md`「同期が要る対」)。REQ への追加漏れは、その gate だけ配備漏れが無音になる
  = ③「効いていない強制を無音にしない」に自分で違反する形の穴になる
- `charter.md` の不在は doctor が `partial` として可視化する (未決台帳の検査が判断材料ごと
  消えるため)。gate 側でも、未決 ID を参照する WO は charter 不在で落ちる

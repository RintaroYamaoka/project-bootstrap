# 0024 — 上流の品質は、下流のテレメトリ (エスカレーション・再試行・差し戻し・トークン) で測る

- **Status**: Accepted
- **Date**: 2026-08-07
- **Deciders**: Rintaro Yamaoka
- **References**: ADR 0022 (上流の統合) / ADR 0023 (発注 gate) / `scripts/velocity.sh` (同型の先例) / 旧 `kanban-flow` `DESIGN.md` 14 節

---

## Context (背景)

前身プラグイン `kanban-flow` は、自身の設計文書でこう結論して自己改善ループを断念していた。

> bootstrapの自己改善ループは「テストが落ちた」「hookが発火しなかった」のような機械的に
> 検出できるシグナルに支えられている。**kanban-flowの失敗は性質が違う——判断ミスであり、
> 機械的には検出できない**

代替として置かれたのは `bandwidth-check` skill (計画担当の負荷を人間が定期的に眺める)
であり、これは計測ではなく内省である。結果として、カード粒度の基準・レビューの要否・
テンプレートの節構成といった運用パラメータが**良くなる経路が存在しなかった**。

しかしこの前提は誤っている。上流の曖昧さは消えるのではなく **下流へ移動する**:

- 仕様に穴があれば AI は止まって人間を呼ぶ → **エスカレーション回数**
- 完了条件が弱ければ修正を繰り返す → **再試行回数**
- 意図とずれた物が出来れば作り直す → **差し戻し回数**
- 探索範囲が広がれば読む量が増える → **トークン消費**

いずれも観測可能である。従来の「この設計を協力会社へ渡したら何人月か」という問いが
「この設計を AI へ渡したらどれだけのトークンと計算資源を使うか」に変わっただけで、
**上流の曖昧さを下流の資源投入で吸収する構造は同じ**であり、したがって同じように測れる。

## Decision (決定)

**検収 (`accept` skill) のたびに、WO 1 枚あたりの実績を
`docs/bootstrap/commission/metrics.tsv` に 1 行追記する。**

```
wo_id  slug  ordered  accepted  retries  escalations  rejections  budget_tokens  actual_tokens  escalation_sections
```

最重要の列は **`escalation_sections`** — 「AI が止まって人間を呼んだとき、その穴は WO の
**何節**にあったか」を節番号の `,` 連結で記録する。集計は `scripts/wo-metrics.sh`。

判定の指針は「そのエスカレーションを防ぐには**どの節に何を書いてあればよかったか**」で、
その節番号が答えになる。

この数字の用途は 2 つ:

1. **どの事前条件が効いていないかを名指しする**。節別エスカレーションが特定の節に偏るなら、
   その節の文言か記入の慣行が弱い。散らばるなら WO の粒度が大きすぎる
2. **上流を緩めてよいかを根拠で決める** (原則④)。事前レビューを小さい WO で省略してよいか、
   節を減らしてよいかを、勘でなくこの数字で判断する

**エスカレーション 0 を良い値として扱わない**。事前条件が過剰で発注コストを払いすぎている
可能性と区別がつかないため、必ず `[ズレ]` 件数 (検収で意図と違った行) と並べて読む。

**採用しなかった代替案:**

- *人間が定期的に負荷を振り返る (`bandwidth-check` 方式)* — 前身が実際に採り、パラメータが
  一度も更新されなかった。内省は計測ではない
- *トークンだけを見る* — 大きい作業ほど増えるので、上流の質の指標にならない。
  「穴に当たって止まった回数」の方が直接的
- *hook でエスカレーションを自動計測する* — 「今のは仕様の穴による停止か、正常な確認か」は
  既約な判断で、機械では分類できない。記録は `accept` の人間 (と AI) の判断に残す

## Consequences (結果)

### 良い影響

- kanban-flow が「原理的に不可能」として放棄した上流の自己改善ループが、下流のテレメトリを
  信号にすることで成立する
- テンプレートの節が「増やしたい気持ち」でなくデータで増減できる。ADR 0023 が固定した
  12 節を将来変えるときの根拠がここにある
- `velocity.sh` (下流のレビュー濃度) と対になり、④の適用範囲が発注まで広がる

### 悪い影響 / トレードオフ

- **self-report である**。採点者 (発注者) と律速が同一人物の間、「エスカレーションを
  呼ばなかった」は「穴が無かった」とは限らず「AI が勝手に解釈して進んだ」でも 0 になる。
  この限界は `wo-metrics.sh` の出力末尾と `accept` skill に明記した
  (限界を無音にしない = ③ の自己適用。`velocity.sh` と同じ扱い)
- 記録が人手なので、書き忘れると無音で欠測する。hook で強制はしない —
  「記録したか」を検出できる信号が無く、作れば proxy になるため
- サンプルが十分たまるまで (WO 十数枚) は、どの結論も出せない

### 移行後に必要な保守

- `escalation_sections` の節番号は ADR 0023 の 12 節に対応する。節構成を変えたら、
  過去の行の番号の意味が変わる — 変更時は `metrics.tsv` に区切りコメント行
  (`# --- schema v2 since YYYY-MM-DD ---`) を入れ、集計を跨がせない
- 十数枚たまったら `incident` skill で 1 度振り返り、得られた教訓を memory へ昇格させる

## 追記 — schema v2: 停止条件の突合と人間時間 (2026-08-07)

実運用 0 行のうちに、列を 4 つ末尾に足した (移行対象の既存行は無い):

```
… escalation_sections  retry_limit  human_order_min  human_run_min  human_accept_min
```

**`retry_limit` (停止条件の突合)**: 発注 gate (`block-commit-if-wo-incomplete.sh`) が強制
できるのは 10 節を「書いたか」までで、「守られたか」を見る仕組みが無かった。予算は
`budget_tokens`/`actual_tokens` の対で既に突合できたが、再試行は宣言値の列が無く突合不能
だった。WO frontmatter の `retry_limit` を検収時に転記し、`retries > retry_limit` /
`actual_tokens > budget_tokens` を「停止条件を破って走った」の信号にする。実行中に止める
機構は作らない — 「今のは同一失敗の再試行か、別の試行か」は既約な判断で、hook で数えれば
proxy になる (本文の「hook でエスカレーションを自動計測する」を採らなかった理由と同じ)。
破られた事実が検収で必ず可視化されれば、④ の取引材料としては足りる。

**`human_order_min` / `human_run_min` / `human_accept_min` (人間時間)**: この開発体制の
律速資源は人間のレビュー帯域 (全 repo 共有の単一資源) だと結論しているのに、その資源が
どの工程 (発注まで / 実装中の対応 / 検収) に溶けているかの計測が無かった。「次にどこを
自動化するか」はこの数字でしか決められない。5 分刻みの粗い自己申告でよい — 精度より
偏りの検出が目的。未計測は `-` (欠測として集計から除外、0 と混同しない)。

`wo-metrics.sh` は v1 行 (10 列) の 11 列目以降を未記録として読むので、区切りコメントは
必須ではないが、新規作成時に `# schema v2 (2026-08-07): …` を 1 行目に書く (accept skill)。
節構成の変更時の区切りコメント規約 (本文「移行後に必要な保守」) は従来どおり。

project-bootstrap v0.34.0 — 全体解説

普段どおり頼むだけ。
間違えそうな瞬間だけ、自動で止まる。

このプラグインは「腕のいい開発者なら自然にやる規律」を、AI が忘れても・あなたが知らなくても自動で効くガードレールに変えたもの。このページは、AI 駆動で進化し続けた全体像を一度に取り戻すための地図です。

覚えることは 3 つだけ

  1. 普段どおり Claude に頼む。コマンドはほぼ全部 AI が状況を見て勝手に呼ぶ。
  2. 止められたら理由文を読む。理不尽に見えても、たいてい正しく止めている。対処法も理由文に書いてある。
  3. まとまった作業を丸ごと任せたいときだけ「/order で発注して」と言う。これが上流工程の入口。
第 1 章

何のためにあるか — 「気をつけてね」は必ず忘れられる

AI に開発を任せると、同じ失敗が繰り返し起きます。テストを書かずに実装する。「完了しました」と言うが実物を見ていない。git add -A で関係ないファイルを巻き込む。長い会話の途中で、最初に言われた注意を忘れる。

普通の対策は CLAUDE.md に注意書きを増やすことですが、注意書き (advisory) は会話が長くなると必ず薄れます。人間の「今度から気をつけます」と同じです。

このプラグインの答えはひとつ: 注意する代わりに、通り道に関所を置く。commit・merge・新規ファイル作成といった「どんなやり方をしても必ず通る行為」の瞬間に機械が検査し、条件を満たすまで通さない。忘れるかどうかに依存しないので、会話が何時間続いても効き方が変わりません。

設計の 4 原則 (かみ砕き版)

  • ① 分解 — 「良い判断」は強制できないが、「判断を済ませた証拠」は強制できる。だから判断の記録を前進の条件にする。
  • ② 信号選び — 「〜っぽい言葉」ではなく「行為そのもの」で検知する。言葉には無限の言い換えがあり、必ずすり抜けられるから。
  • ③ 配備の可視化 — 効いていない関所ほど危ない (守られている気になる)。だからセッション開始時に点検結果を画面に出す。
  • ④ 計測つきの取引 — ルールを緩めたくなったら、勘でなく数字 (後述の metrics) で決める。
第 2 章

開発の流れ全体図 — 発注から検収まで

v0.33.0 から、このプラグインは実装だけでなく上流 (発注) から検収までを一貫して担います。外注管理と同じ構図です: あなたが発注者、AI が施工者。

重要なのは、関所がなぜ commit と merge に集中しているかです。書き込む方法は無数にあります (Edit ツール、formatter、sed、リダイレクト…)。方法を 1 つずつ塞ぐのはモグラ叩きで必ず漏れます。しかしどんな方法で書いても、成果にするには必ず commit を通る。だから全方式が合流する一点に関所を置く — これがこのプラグインの背骨です。

第 4 章

止める関所 — 24 本あるが、覚えるのは 6 場面でいい

hook は 24 本ありますが、あなたの体感としては「この 6 場面で止まる」だけです。止まったら赤い理由文に対処法が書いてあります。

こうすると止まるなぜ対処
契約 (WO) も並列判定も無いまま、新しい実装ファイルを作る「何を作ってよいか」を決めた記録なしに実装が始まるのを防ぐ「/order で発注」するか、AI が逐次判定を 1 行記録して続行
テストの無い実装を触る / テスト・lint が落ちたまま commitテスト先行 (TDD) と「落ちたまま進む」の防止先にテストを書く / 落ちを直す (AI が自動でやる)
git add -A・reset --hard・push -f など巻き込み・破壊系関係ないファイルの混入と、履歴・作業の破壊を防ぐ個別 path 指定 / --force-with-lease に矯正される
並列開発中に、自分の担当 (lane) 外のファイルを触る・commit する複数 Claude の同時作業が無音で衝突するのを防ぐ担当レーンに任せる。正当なら lane に 1 行追記
AI レビュー記録なし・動作テスト未完了のまま merge「各自は緑でも合体したら壊れる」を合流の一点で検査レビューと verification を閉じてから merge
保護ブランチへ直 push / 古い checkout から pushmain を PR 経由に限定し、古い状態からの上書きを防ぐPR を作る / pull して最新化

止めないものも 3 種類あります: セッション開始時の点検表示 (古い checkout・残った worktree などを見せるだけ)、本番デプロイ・データ修復の瞬間に過去の教訓メモを目の前に出す表示、並列判定の促し。これらは「判断はあなたと AI に残し、忘れることだけを防ぐ」役です。

ローカルで止めても、GitHub の Merge ボタンは素通りする問題

hook はあなたの手元でしか効かないので、同じ検査を GitHub Actions (CI) にも二重化してあります (テスト・動作テスト完了・配備点検・引退名チェックの 4 本)。今日のリリース PR #26 もこの 4 本を通ってから merge されています。

第 5 章

スイッチの場所 — 「フォルダを置く」が採用宣言

強い関所は全部 opt-in です。特定のフォルダやファイルが repo にあるときだけ発火し、無ければ何も起きません。つまり「この repo で何が効いているか」は、この表と repo を見比べれば分かります。

repo に置く物効き始めるもの
docs/bootstrap/commission/上流工程まるごと (契約なしの実装 block・発注 commit の完全性検査)
docs/bootstrap/sprint/並列判定の関所 (新規ファイル作成前に sprint 判定を要求)
docs/bootstrap/verification/動作テスト未完了の merge を block
.bootstrap/lintcommit 時の lint 検査 (この commit が運ぶファイルだけ)
.bootstrap/arch依存方向・層違反の block
.bootstrap/protected指定ブランチへの直 push 禁止
.bootstrap/retired改名で引退した古い名前の混入 block
.bootstrap/wip同時並列レーン数の上限
.bootstrap/lane (worktree ごと)担当外ファイルの編集 block (sprint-plan が自動生成、手で作らない)

常時効くもの (置き物不要): TDD、危険 git 操作の矯正、レビュー無し merge の block、本番操作時の教訓表示。

注意: plugin の更新 ≠ 各 repo で効いている。今日のようにプラグインを更新したら、各 repo のセッション開始時の点検 (doctor) が古さを教えてくれます。「merge したのに効いてない」の大半はこれです。

第 6 章

数字で回す改善ループ — 今日 v0.34.0 で強化された部分

検収 (/accept) のたびに metrics.tsv へ実績が 1 行残り、scripts/wo-metrics.sh で集計できます。これは「ルールを増やすか・緩めるか」を勘でなく数字で決めるための装置です。読み方だけ覚えれば十分:

数字がこう出たら意味打ち手
エスカレーション (AI が止まって人間を呼んだ回数) が特定の節に偏る契約書テンプレートのその欄が弱いその節の書き方を強化
エスカレーションが全体に散る1 枚の契約が大きすぎるWO を小さく割る
停止条件の超過 (再試行上限・予算を破って走った) v0.34 新設実装の失敗である前に「止まり方の設計」の失敗停止条件 (10 節) の書き方を直す
人間時間が特定工程に偏る v0.34 新設あなたの時間 = 唯一の律速資源の溶け先そこが次の自動化投資先
エスカレーションが 0 のまま続く良い値とは限らない。事前準備が過剰か、AI が勝手に解釈して進んだか検収の [ズレ] 件数と並べて読む

v0.34.0 ではもう 1 つ、「人間の手動確認を使い捨てにしない」仕組みが入りました。動作テストであなたが手で確認した項目を閉じるとき、AI が「これ、次回からテストか監視で自動化できませんか」と一度聞いてきます。OK すれば恒久化され、同じ確認は二度と手動で来ません。開発が大きくなるほど効く変更です。

第 8 章

今の状態と、次の一手

設計は完成度が高い一方、上流工程 (発注→検収) はまだ実運用 0 件です。過去に 2 回作られた上流の仕組みは、どちらも設計段階では筋が通っていたのに「重くて使われず」死にました。今の設計がそれを超えているかは、実プロダクトで契約書を 1 枚通して初めて分かります。

次の一手 (これだけ)

あなたのプロダクト repo の次のまとまった作業で 「commission を採用して、/order で発注して」 と言う。それだけで charter 作成 → 契約書 12 節 → 敵対レビュー → 発注 → 実装 → 検収 → 実績 1 行目、まで AI が回します。検収時に「何分使った?」と聞かれたらざっくり答えてください。

# charter — 不可逆だけを、1 ファイルに

## この skill が答える問い

> **後から覆すコストが高い判断は何か。それ以外は何を決めないでおくか。**

可逆な判断はここに書かない。コードとテストが正本であり、決め直せばよい。
ここに書くのは、間違えたときに書き直しでは済まないものだけ。

## なぜファイルが 1 つなのか

前身の 2 実装 (upstream-process / kanban-flow) は上流成果物を 13 種類のファイルに割り、
どちらも「重くて結局使わない」で死んだ。**書き分けの規則そのものが記憶の負担になり、
負担が使用を止めた**。原因は各ファイルの中身ではなく、ファイルを増やしたこと自体にある。

だから永続ファイルは `charter.md` 1 つに固定する。増やしたくなったら、それは
「WO に書くべき個別の話」か「そもそも書かなくてよい可逆な判断」のどちらかであることが多い。

例外は 2 つだけ:

- **不可逆な *アーキ* 判断** → `docs/decisions/` の ADR。状態遷移 (提案/採用/破棄/置換) と
  撤回の記録が要るので、追記専用の charter とは別機構が要る
- **個別作業の指示** → `docs/bootstrap/commission/wo/<id>-<slug>.md` (`order` skill)

## 進め方

### 0. 採用

`docs/bootstrap/commission/` が無ければ、雛形を置く (これが採用宣言 = hook の opt-in)。

```bash
cp -r "$CLAUDE_PLUGIN_ROOT/templates/docs/bootstrap/commission" docs/bootstrap/
```

### 1. 不可逆の候補を洗う

greenfield なら壁打ちで、brownfield なら**既存コードと実データから**洗う。
brownfield で既存 docs を根拠にしない — それ自体が負債の可能性がある。

不可逆になりやすいのは経験上この 3 種:

| 種別 | 例 | なぜ不可逆か |
|---|---|---|
| **データ所有と形** | 誰がどのデータを持つか / schema の形 | migration が高くつく。過去データは遡って作れない |
| **外部契約** | 公開 API の形・版・外部サービスの選択 | 相手がいるので単独で戻せない |
| **アーキテクチャの継ぎ目** | layer の切り方・port の位置 | 全体に波及する。`.bootstrap/arch` に落ちる |

**中心仮説** (この製品が成り立つために真であってほしいこと) も 1 行で書く。
これは不可逆ではないが、覆ったときに全部が無駄になる唯一の項目なので、
可能なら最初の WO で最短経路を 1 本通して確かめる。

### 2. 「決めない」を明示的に決める

洗った候補のうち、いま決める必要が無いものは **未決台帳に OPEN で載せる**。
これが両前身プラグインから引き継ぐ唯一の不変条件の実装である:

> 未決定事項は「観測される・決定される・台帳に載る」のいずれかであり、
> **無音で埋まってはならない**。AI・実装者・自分自身の誰によっても。

未決を台帳に載せておくと、それに依存する WO を発注しようとした瞬間に
`block-commit-if-wo-incomplete.sh` が止める。**この 1 行を書くことが、
後で自分を止める仕掛けを置くことになる**。

### 3. 書く

`charter.md` の 5 セクションを埋める。全部埋まらなくてよい —
埋まらなかったものは未決台帳に 1 行入れる (欠落を無音にしない)。

**決定ログと制約の違い**: 決定ログは日付つき・理由つきの個別判断。制約は日付を持たず、
プロジェクト全体で常に真であるべき前提。決定ログの行が十分 evergreen だと分かったら
制約へ昇格させてよい。

### 4. 継ぎ目の所有者を 1 人決める

アーキテクチャの境界 (contract / port / 公開型) を持つ人を 1 人決めて charter に書く。
ソロ運用なら自分。**所有者以外は継ぎ目を変えない** — これが WO の 3 節「変更禁止範囲」の
既定の中身になる。

## 再発火するとき

`charter` は t=0 だけの儀式ではない。以下のときに戻ってくる:

- **不可逆判断が新しく必要になった** (新しい外部連携・schema の作り直し)
- **未決が決着した** — 台帳の行を CLOSED にし、決定ログに 1 行足す
- **中心仮説が覆った** — このときは目的と不変のコアを書き換える。書き換える前に、
  その前提を 4 節で参照している **進行中の WO を grep する**。承認済みの指示の下から
  前提を黙って抜くと、実装者の成果物が実装者の落ち度の顔をして壊れる

## やらないこと

- **企画書・業務フロー図・機能一覧・非機能要件書・画面遷移図・ER 図・CRUD 表・
  外部インタフェース一覧・RACI 表を作らない**。前身プラグインがカタログとして持っていたが、
  実戦投入された形跡が一度も無かった。必要になった一部だけ、WO か決定ログの 1 行として都度書く
- **進捗・状態を書かない**。git log と WO の frontmatter が持つ
- **可逆な判断を書かない**。増えるほど charter が読まれなくなり、読まれない正本は正本でない

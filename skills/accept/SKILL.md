# accept — 検収し、上流の品質を測る

## この skill が答える問い

> **返ってきた物は、発注した物か。** そして
> **その作業指示は良かったのか — どの節が薄かったのか。**

前半は受け入れ判定、後半は自己改善のための計測。**後半を省くと、テンプレートが
良くなる経路が存在しなくなる**。前身プラグインはどちらも後半を持たなかった。

## 前提 — 既存の関所は先に通っている

`accept` は merge 関所の代わりではない。merge の時点で既に:

- `block-unreviewed-merge.sh` が AI レビュー記録 (`verdict: approve`) とテスト実走を要求済み
- `block-merge-if-verification-unclosed.sh` が verification plan の OPEN 行ゼロを要求済み

`accept` が見るのは**それらが見ていないもの** — 「実装が正しいか」ではなく
**「発注した意図と一致しているか」**。テストは緑でも意図と違う物が出来ていることはある。

## Step 1 — 独立コンテキストで突合する

**実装したセッションに検収させない。** `pre-review` と同じ理由で、
実装の文脈を引き継いだセッションは自分の仕事を採点することになる。

渡すもの: WO 1 枚 + 実装差分 (`git diff <base>...<branch>`) + リポジトリ。
渡さないもの: 実装中の会話ログ。

突合の指示:

> WO の 8 節の DoD を 1 行ずつ、9 節のオラクルで実際に確認しろ。
> 各行に `[OK]` / `[ズレ]` / `[要判断]` を付けろ。**差分を読んだ印象で付けるな** —
> オラクルを実行するか、実行できないなら `[要判断]` にしろ。

| 判定 | 意味 |
|---|---|
| `[OK]` | オラクルを実行し、DoD どおりだった |
| `[ズレ]` | 実装が DoD と違う (足りない / 余計 / 別物) |
| `[要判断]` | オラクルが実行できない・DoD の解釈が割れる・判断が要る |

## Step 2 — 4 つの追加検査

DoD の突合だけでは取りこぼすものがある。

1. **検算**: DoD 行数 = 判定行数。合わなければ取りこぼしている
2. **越境**: 差分に **3 節 (変更禁止範囲)** の file や契約が含まれていないか
   (`git diff --name-only` と 3 節の glob を突合)
3. **範囲外**: 差分が **2 節 (作業範囲)** に収まっているか
   (lane gate が効いていれば通っているはずだが、hook を経由しない経路の最終網)
4. **定義ドリフト**: 実装が導入した新しい語・型・フィールド名を列挙し、
   charter / 既存コードに**同じ概念の別名**が無いか grep する。
   改名していたなら `.bootstrap/retired` に登記されているか (癖⑩ / ADR 0021)

## Step 3 — 判定

**`[ズレ]` か `[要判断]` が 1 行でもあれば差し戻す。**

- WO の frontmatter `rejections` を +1 し、`status` を `ordered` に戻す
- 何をどう直すかを WO 本体に反映する (指摘だけ口頭で渡さない)
- **差し戻しは失敗ではなく設計どおりの動作**。ただしカウンタは残る — それが Step 4 の材料

全行 `[OK]` なら受け入れる: `status: accepted`、`accepted: <今日>`。
人間 (発注者) が読むのは**一言結論と `[要判断]` 行だけ**でよい。
全 diff を人間が直列で読むのは帯域律速なので、最初からしない設計にする (原則④)。

## Step 4 — 実績を 1 行残す (ここが自己改善ループの本体)

`docs/bootstrap/commission/metrics.tsv` に TAB 区切りで 1 行追記する。

```
<wo_id>	<slug>	<ordered>	<accepted>	<retries>	<escalations>	<rejections>	<budget_tokens>	<actual_tokens>	<escalation_sections>
```

`escalation_sections` が最重要の列 — **AI が止まって人間を呼んだとき、その穴は WO の
何節にあったか**を `,` 区切りの節番号で書く。穴が無ければ `-`。

例: 実装中に「この異常系どうする?」で 2 回止まったなら `6`。
「契約を変えていいか」で止まったなら `3` か `11`。

判定に迷ったら、そのエスカレーションを防ぐには**どの節に何を書いてあればよかったか**を
考える。それが答えの節番号になる。

## Step 5 — 片付ける

- WO ファイルは**消してよい** (git 履歴が正本)。堆積した指示書は誰も読まない
- charter の未決台帳で、この作業を通じて決着したものを CLOSED にし、決定ログに 1 行足す
- worktree は merge の**後**に撤去する (先に撤去すると関所の信号が消える)

## 定期的に読む

```bash
scripts/wo-metrics.sh
```

節別エスカレーションが特定の節に偏るなら、その節のテンプレート文言か記入の慣行が弱い。
散らばるなら WO の粒度が大きすぎる。**どちらも 0 が続くなら事前条件が過剰**な可能性がある
— 0 は必ずしも良い値ではない。

この数字は、上流を緩めてよいかを勘でなく根拠で決めるためにある (原則④「計測つきの取引」)。
限界も正直に持つ: 採点者と律速が同一人物の間、これは self-report に近い。
「エスカレーションが 0」は「穴が無かった」とは限らず、「AI が勝手に解釈して進んだ」でも 0 になる
— だから `[ズレ]` の件数と必ず並べて読む。

## 事故が起きたら

検収で見つかった `[ズレ]` が**同じ節に 2 回以上**由来するなら、それは個別のミスではなく
構造の症状である。`incident` skill をロードして記録し、教訓を memory へ昇格させる
(commission 専用の incident 機構は作らない — 1 つの機構を共有する)。

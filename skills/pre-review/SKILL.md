# pre-review — 実装前に、AI を敵として使う

## この skill が答える問い

> **この作業指示を渡された優秀な実装者なら、着手前に何を質問してくるか。**

従来のウォーターフォールが現実に成立していた理由の一つは、下流の人間が単純な命令実行者では
なかったことにある。優秀な実装者は仕様の矛盾を質問し、既存機能への影響を警告し、
より保守しやすい代案を出した。**公式には下流工程だが、そこを通って上流の設計は修正されていた。**

AI エージェントも質問はできる。だが疑問のたびに停止して人間へ確認していては、
長時間自律稼働させる意味が消える。だから **従来は下流から出ていた質問と異論を、
事前に予測して設計へ組み込む**必要が生じる。この skill がその工程である。

## なぜ実装 *前* なのか

前身プラグイン (kanban-flow) も敵対的 AI レビューを持っていた。ただし
**統合サインオフ = 実装が終わった後**にしか置いていなかった。そこで見つかる穴は、
既にトークンを払って作られたものの穴である。

同じレビューを発注の前に置くと、同じ穴が **1 回の対話**で閉じる。
上流の一行が下流の何百万トークンを左右する以上、レビューは安い側に置く。

## 実施の条件 — 独立したコンテキストで

**WO を書いたセッションにレビューさせない。** 自分の仕事を自分で採点するのと同型の
バイアスがかかり、書いたときの思い込みがそのまま素通りする。

- 別セッション (別ターミナル / `/clear` 後) で、WO と charter だけを渡す
- または subagent を **read-only** で起動する (breadth 用途なので隔離も wip も不要、ADR 0005)
- ソロ運用ではこれが「第二の目」の代替になる。多者体制なら人間のレビュアーが兼ねてよい

渡すもの: WO 1 枚 + charter の該当セクション + リポジトリへの読み取りアクセス。
**渡さないもの**: WO を書いたときの会話ログ (思い込みごと伝染する)。

## 5 つの観点 (固定)

レビュアーへの指示は「良くしてくれ」ではなく **「落とすつもりで読め」**。
観点を固定するのは、自由記述にすると褒めて終わるため。

### 1. 曖昧さ — 解釈が 2 通り以上できる箇所

> この指示のうち、**別々の実装者が読んだら別の物を作る**文はどれか。
> 特に: 名前 / 分類 / 「無い」の扱い / 0 と未観測の区別 / 順序 / 「など」「適切に」。

### 2. 矛盾 — 既存設計と衝突する箇所

> 7 節の継ぎ目・4 節の既存条件は、**現在のコードの実態**と一致しているか。
> 3 節の変更禁止範囲を守ったまま 8 節の DoD に到達できるか (到達不能なら仕様が矛盾している)。

到達不能性は最も価値の高い指摘。実装が半分進んでから発覚すると全損になる。

### 3. 未定義の異常系

> 入力が空 / null / 最大 / 重複 / 順序違い / 外部が落ちている / 権限が無い / 途中で失敗した —
> それぞれで何が起きるべきか、6 節から一意に決まるか。決まらないものを列挙しろ。

### 4. 抜け道 — DoD をテストだけ通して実質を満たさない経路

> 8 節の各 DoD を、**意図を満たさずに**通す最も安い実装は何か。
> 例に合わせた固定値を返す / 中身のない stub / テスト入力を検知して期待値を返す /
> 採点コードそのものを書き換える。

これは AI 固有の失敗クラスで、「もっと厳しくレビュー」では消えない
(採点表に手が届くのが原因)。緩和は `verification` skill の held-out oracle と
metamorphic テスト (ADR 0016) — 指摘が出たら 9 節のオラクルをそちらの形に直す。

### 5. 停止条件の過不足

> **止まるべきなのに止まらない**条件はどれか (10 節に無いエスカレーション事由)。
> **止まるべきでないのに止まる**条件はどれか (過剰なエスカレーションは自律性を殺す)。
> `retry_limit` と `budget_tokens` は、8 節の作業量に対して妥当か。

## 記録と決着

指摘は WO の 12 節の表にそのまま積む。**各行の終わり方は 2 つだけ**:

| 状態 | 意味 | やること |
|---|---|---|
| `closed` | WO を直して穴を閉じた | 該当する節を修正する。指摘欄には何を直したかを残す |
| `deferred:<未決ID>` | いま決めない、と決めた | charter の未決台帳に行を足し、**10 節のエスカレーション条件にも書く** |

`deferred` は「無視」ではない。**名前のついた既知の空白**にして、そこに当たったら
AI が止まって人間を呼ぶようにするのが条件。名前をつけずに先送りするのが、
両前身プラグインが共通して禁じていた「未決を無音で埋める」そのものである。

`open` のまま残っている行が 1 つでもあれば、発注 commit は
`block-commit-if-wo-incomplete.sh` が落とす。表が空 (レビュー未実施) も同様に落ちる —
**未実施と「指摘ゼロ」を区別する**。

## 空振りしたときの読み方

指摘がほとんど出ない状態が続くなら、次のどれかである:

1. WO の粒度が十分小さく、テンプレートが効いている (良い状態)
2. レビュアーが協力的になっている (「落とすつもりで読め」が効いていない)
3. 事前条件が過剰で、発注コストを払いすぎている

区別する材料は `scripts/wo-metrics.sh`。**事前レビューで指摘ゼロなのに実装中の
エスカレーションが多い**なら 2、**どちらもゼロが続く**なら 3 の可能性がある。
勘で緩めず、この数字を根拠にする (原則④「計測つきの取引」)。

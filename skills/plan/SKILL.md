# /plan — 探索 → 計画 → 提示

このスキルは、自明でない作業を始める前に **構造化された計画書** を出力するためのもの。

**鉄則**: このスキルの実行中は **実装を行わない**。`Edit` / `Write` ツールを使わない。`Read` / `Grep` / `Glob` だけで探索し、計画を出力したら停止する。ユーザーの承認を得てから初めて実装フェーズに移行する。

> 正直な注記: この「実行中は Edit/Write を使わない」は **hook 強制ではなく advisory (規約)** — plan 実行中かどうかを hook は観測できない。downstream gate が居るのは**新規 source 面の作成** (`block-unplanned-feature-build.sh`) と **merge** (`block-merge-if-verification-unclosed.sh`) に対してだけで、**plan 中の既存 file への Edit を止める機構は無い (そこは純 advisory)**。

呼び出し方:
- ユーザーが `/plan <タスク>` と打ったとき
- 自明でない作業を依頼されたが、計画なしで実装を始めようとしているとき (自発的に呼ぶ)

## ワークフロー

### Step 1: タスクを 1 文で言い換える

依頼内容を自分の言葉で再構成する。曖昧な点があれば明確化を求める、または仮定を明示する。

### Step 2: スコープを定める

- **スコープ内**: 何をする
- **スコープ外**: 何をしないか (明示することが重要 — AI は放っておくとスコープを広げる)
- **成功条件**: 何が満たされたら done か。後でテストの形に翻訳できる粒度で書く

### Step 3: 既存コンテキストを read-only で探索する

実装に触れる前に、以下を `Read` / `Grep` / `Glob` で読む:

- 編集対象になりそうなファイル
- そのファイルを呼び出している / 呼び出されているファイル
- 関連するテスト (既存の振る舞い仕様)
- 作業対象エリアのディレクトリ構成

**この時点で `Edit` / `Write` を行わない**。読むだけ。

探索範囲が広いなら、この読みを **read-only の Workflow ファンアウト**に下請けさせてよい (ADR 0005 の breadth 顔: 隔離不要・`wip_limit` 非対象・gate 摩擦ゼロ)。ただし `/plan` の鉄則を保つ — 起動する Workflow は **read-only 専用** (lane worktree を作らない・mutation させない)。mutation を伴う lane を出すのは `/sprint-plan` の役割であって `/plan` ではない (この区別が「判定の前に実装しない」の境界)。

### Step 4: 最小ステップに分解する

タスクを、次の条件を満たす変更単位に分解する:

- 責務が 1 つ
- 入力 → 出力の契約が明確
- 失敗時の挙動が明確
- **テストとして書ける** (Red フェーズで failing テストを書ける粒度)

これらの形で記述できないステップは、設計がまだ不明確。明確化してから次に進む。

### Step 5: 前提を検証する

外部依存を確認する:

- **外部ライブラリ呼び出し** → 推測ではなく実際のシグネチャを確認 (`Read` でドキュメントや型定義)
- **他ファイルからの import** → そのシンボルが存在するか確認
- **型の形** → 型定義を読む。フィールドを捏造しない
- **設定 / 環境変数** → 設定済みか確認
- **repo に無い外部の事実** (3rd-party の挙動 / API セマンティクス / 「X は可能か」) → 記憶からの推測でなく **`/deep-research`** (web を多角検索し主張を相互照合する read-only の breadth 腕、ADR 0005) で裏取りする。これは「オラクルを AI の外に置く」(`verification` skill) の web 版 — read-only なので `/plan` の鉄則を破らない。使えない環境なら `WebSearch`/`WebFetch` で代替し、得た事実は引用つきで前提欄に残す

検証できなかった前提は計画書の **「未検証 / リスク」** 欄に記録する。実装フェーズで検証してから使う。

### Step 6: 計画書を出力する

以下のフォーマットで出力する:

```markdown
## タスク

<1 文で言い換え>

## スコープ

**スコープ内:**
- ...

**スコープ外:**
- ...

## 成功条件

- ...

## 探索したコンテキスト

- `path/to/file.ts:LL` — <要点>
- `path/to/test.ts:LL` — <既存の振る舞い>
- ...

## ステップ

### Step 1: <名前>
- **責務**: ...
- **入出力**: ...
- **失敗時の挙動**: ...
- **テスト観点 (Red で書く failing テストの内容)**: ...

### Step 2: <名前>
...

## 検証済みの前提

- `lib.foo()` のシグネチャ: <確認済み>
- `Module.bar` の型: <確認済み>
- ...

## 未検証 / リスク

- ...

## 質問 / 仮定 (あれば)

- ...
```

### Step 7: 停止する

計画書を出力したら **実装に進まずに停止する**。
ユーザーが計画を承認するまで、コードの編集は行わない。

承認後、TDD ワークフロー (Red → Green → Refactor) に移る。各ステップは Red フェーズで failing テストを書くところから始める (詳細は `project-bootstrap` skill 参照)。

## 動作テスト (verification) は plan 時にアンカーする

成功条件 (Step 2) は「コードの正しさ」を超えて**継ぎ目 (cross-repo 契約 / 要件 / 「実物を見ずの完了」/ 環境)** を含むことが多い。これらは repo 内 unit test の射程外で、緑のテストが誤った契約を固定して false confidence を配る (ADR 0007 / mood incident)。だから**動作テストの設計は実装の後でなく plan 時に始める** — 実装がまだ無いので実装追認テストにならない (TDD が test を先に書くのと同型)。

feature を実装する計画なら、`verification` skill をロードして**意図と「跨いだ境界」から検証すべき挙動を導き** (実装からでなく)、`docs/bootstrap/verification/<branch>.md` の骨子 (各行に外部オラクル) を起こす。最終オラクルが人間にしか出せない行は `HUMAN` でフラグする。統合時に `block-merge-if-verification-unclosed.sh` がこの plan の clozure を要求する。

## 例外処理

- **計画が大きすぎる** と判断したら、「1 タスクには大きすぎる、分割を提案する」と伝える
- **依頼内容そのものを見直すべき** (例: そもそも修正不要、別箇所が原因、要件矛盾) と判断したら、計画書ではなく「再考の提案」として伝える

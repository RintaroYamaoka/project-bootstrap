# order — 引き渡し契約を確定させ、発注する

## この skill が答える問い

> **人間がいなくても AI が走り切れるだけの情報を、渡し切ったか。**

自律稼働時間を延ばす唯一の方法は、開始前に与える情報を増やすことである。
質疑応答を減らすほど AI は途中で新しい情報を受け取れず、仕様に穴があれば
**質問せずにもっともらしい解釈を選ぶか停止する**。その手戻りは下流のトークンで返ってくる。

## 成果物

`docs/bootstrap/commission/wo/<NNNN>-<slug>.md` 1 枚。様式の権威は
`templates/docs/bootstrap/commission/wo/TEMPLATE.md`、判定エンジンは `hooks/lib/wo.sh`。

## 進め方

### Step 1 — 起票して draft のまま探索する

TEMPLATE.md を複製し、`status: draft` のまま作業する。**draft は完全性 gate の対象外**
なので、途中の状態で自由に commit してよい (起草を止めると、checkpoint を保存するために
節をノイズで埋める誘因が生まれ、gate が自分の bypass を作る)。

### Step 2 — 探索を発注側で終わらせる (7 節・継ぎ目)

Read / Grep で **実在する** API・型・関数を名指しで埋める。予測で書かない。
ここが埋まっていると実装者は再探索しない — これは前身 2 実装のうち実運用で効果が
確認できた数少ない仕組みで、そのまま継承している。

書き終えたら **実在検算**: 7 節に挙げた識別子を 1 つずつ grep し、見つからないものが
あれば消すか直す。ここで嘘を書くと、実装者はそれを信じて 1 往復を無駄にする。

### Step 3 — 委譲する空白に名前をつける (11 節)

「決めてよいこと」「決めてはいけないこと」の**両方**を書く。
片方だけだと、書かれていない側が「全部こちらが決めた」と読まれ、AI を
「空白を無音で埋めるしかない位置」に置く。これも両前身が独立に到達した仕組み。

### Step 4 — 自律稼働の事前条件を埋める (3・5・6・10 節)

前身 2 実装がどちらも**持っていなかった 4 つ**。ここが今回の中心なので手を抜かない。

| 節 | 何を書くか | 空だと何が起きるか |
|---|---|---|
| 3 変更禁止範囲 | 触ってはいけない glob と、コードでない契約 | 「動かすため」に契約を書き換える |
| 5 優先順位 | 2 つの望ましさが衝突したときの取り方 | AI が勝手に片方を選び、後で全部やり直す |
| 6 例外時の判断方法 | 未定義の異常系に当たったときの既定方針 | 停止するか、握り潰す (罠 1: silent failure) |
| 10 停止条件 | 再試行上限・予算上限・エスカレーション条件 | 同じ失敗を延々と再試行してトークンを焼く |

**エスカレーション条件の書き方**: 「困ったら聞いて」は条件ではない。
*何が観測されたら* 呼ぶのかを書く。既定で入れておくとよいのは
「11 節の決めてはいけないことに触れる判断が必要になったとき」
「3 節を変えないと DoD を満たせないと判明したとき」の 2 つ。

### Step 5 — 完了条件と検証方法を対にする (8・9 節)

DoD は「動く」でなく「観測できる」形。1 行 1 条件、`- [ ] D<N>: `。
9 節で **各行に外部オラクル**を 1 つ与える (テスト名 / read-back クエリ / 実測手順)。
人間しか採点できない行は `HUMAN`。

**検算**: DoD の行数 = オラクルの行数。合わなければ発注 commit が落ちる。
この恒等式は spec-recovery から引き継いだ唯一の部品で、出所タグ 4 種は捨てて検算だけ残した
(「オラクルが良いか」は判断だが「1 対 1 か」は数えられる)。

設計の詳しい作法は `verification` skill が権威 (ADR 0007) — 継ぎ目 7 種・
held-out oracle・metamorphic (ADR 0016) はそちらを読む。

### Step 6 — 事前レビューを通す (12 節)

`pre-review` skill をロードする。**独立したコンテキスト**の AI に仮想下流リーダーとして
仕様を壊させ、出た指摘を全部 `closed` か `deferred:<未決ID>` に決着させる。
表が空のままでは発注できない (未実施と「指摘ゼロ」は別物として扱う)。

### Step 7 — 発注する

```
frontmatter: status: draft → ordered、ordered: <今日>、branch: <実装 branch 名>
```

commit した瞬間に `block-commit-if-wo-incomplete.sh` が 12 節の完全性・検算・
事前レビューの決着・`retry_limit`/`budget_tokens` の数値・OPEN 未決への依存を検査する。
落ちたら**節を埋めるか、status を draft に戻す**。

### Step 8 — bootstrap の既存 gate に翻訳する

**ここが統合の要点。上流の決定を新しい強制機構でなく、既にある gate に翻訳して効かせる。**

```bash
# 2 節 (作業範囲) → lane。以後、範囲外の編集と commit は既存 hook が止める (ADR 0017)
git worktree add ../wt-<slug> -b <branch>
cp /dev/stdin ../wt-<slug>/.bootstrap/lane <<'EOF'
<2 節の glob をそのまま 1 行ずつ>
EOF

# 8/9 節 → verification plan の初期行。merge の precondition になる (ADR 0007)
#   docs/bootstrap/verification/<branch>.md に DoD 各行を OPEN で起こし、
#   9 節のオラクルをそのまま各行の検証手段として書く。HUMAN 行は HUMAN のまま運ぶ

# sprint 判定も同時に記録する (別の判断なので別の記録が要る)
printf '%s\n' "<2 節の代表 glob>  $(date +%F)  <逐次/並列の判定と理由>" >> docs/bootstrap/sprint/.gate
```

3 節 (変更禁止範囲) のうちアーキ境界に相当するものは `.bootstrap/arch` に、
引退した名前は `.bootstrap/retired` に落とす。

### Step 9 — 渡す

実装セッションに渡すのは **WO 1 枚と charter の該当セクションへの参照**だけ。
charter 全文も過去の WO も渡さない。

`/plan` は**再実行しない** — WO が計画書そのものだから (`plan` skill 側にこの例外を明記済み)。

## 粒度

WO 1 枚 = **1 つの branch で端まで通せる単位**。上限は「予算内で終わる」、
下限は「価値の 1 単位が通る」。技術的な作業単位 (「型を足す」) に割らない。

大きすぎて disjoint な leaf 2 個以上に割れるなら、WO は 1 枚のまま
`sprint-plan` に渡して lane 並列にする — **WO の分割と lane の分割は別の軸**。
WO は「何を・なぜ作るか」、lane は「1 枚を安全に並列実行する方法」。

## やらないこと

- 実装しない (この skill は発注文を書くまで)
- WO に進捗を書かない (frontmatter の status と git log が持つ)
- 検収済みの WO を残し続けない — `accept` が metrics.tsv に 1 行残したら、
  WO ファイル自体は消してよい (git 履歴が正本。堆積した指示書は誰も読まない)
